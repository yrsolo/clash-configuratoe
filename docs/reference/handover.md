# Передача репозитория новому владельцу

Это отправная точка для человека, который получает код, вводит **свои** подписки и разворачивает **свой** экземпляр. Знание React не требуется для использования редактора, но для деплоя понадобятся терминал и доступ к Яндекс Облаку.

## Что делает проект

Браузерный редактор собирает группы и правила маршрутизации Clash/Mihomo. JSON хранит схему, положения узлов и настройки; YAML предназначен для клиента. Серверная функция сохраняет рабочие пространства, преобразует подписки и отдаёт опубликованный YAML по постоянной ссылке. Сам проект не продаёт подписки и не создаёт VPN-серверы.

Трафик устройства после подключения идёт через выбранный сервер подписки либо напрямую. API Gateway и Cloud Functions обслуживают редактор и конфигурации; обычный пользовательский трафик через них не проходит.

## Маршрут первого запуска

1. Откройте ссылку на GitHub от владельца репозитория и прочитайте корневой `readme.md`. Если репозиторий приватный, владелец должен предоставить доступ вашему GitHub-аккаунту. Клонируйте репозиторий и перейдите в его папку:

   ```bash
   git clone https://github.com/yrsolo/clash-configuratoe.git
   cd clash-configuratoe
   ```

   Если владелец передал отдельную ветку, после клонирования выполните `git switch ИМЯ_ВЕТКИ`. Если нужна независимая копия для своих изменений, создайте fork на GitHub и клонируйте его адрес.
2. Установите Git, Node.js 24 и npm 11. Для PowerShell-сценария Windows подходит встроенный Windows PowerShell; на macOS/Linux установите PowerShell 7 (`pwsh`).
3. В корне проекта выполните:

   ```bash
   npm ci
   npm ci --prefix serverless/workspace-bridge
   npm run release-check
   npm run dev
   ```

4. Откройте `http://localhost:5173`. Локально можно редактировать, импортировать и экспортировать. Сохранение в облако, публикация и проверка подписки требуют маршрутов серверной функции: один Vite-сервер их не создаёт. Для полного первого запуска переходите к деплою.
5. Если аккаунта ещё нет, пройдите [первичную регистрацию](yandex-registration.md).
6. Пройдите [пошаговый деплой](yandex-deploy.md), сначала на служебном HTTPS-домене API Gateway. Покупать домен заранее не требуется.
7. Настройте [свои подписки и базовую схему](starter-configuration.md).
8. Подключите [клиент своего устройства](clients/README.md).
9. Сохраните JSON-резервную копию и изучите [обслуживание, откат и ограничения](operations.md).

## Что сделать владельцу перед отправкой ссылки

В опубликованной ветке должны быть исходники, lock-файлы, `default/new.json`, `deploy/yandex/gateway.openapi.template.yaml`, скрипты и документация. Начальная схема очищена от личных подписок; все источники выключены. `example/Merge.yaml` — синтетический пример импорта, не готовая действующая подписка.

Перед отправкой ссылки проверьте `git status` и `git diff`, включите нужные новые файлы в коммит, выполните `npm run release-check` и отправьте подготовленную ветку в GitHub. Локальные незакоммиченные изменения по ссылке недоступны. Если изменения находятся вне основной ветки, передайте ссылку именно на подготовленную ветку и её имя; после слияния можно использовать обычную ссылку на репозиторий.

Проверьте с GitHub отдельным клонированием, что новый получатель видит документацию и очищенную схему, а установка и проверки из шага 3 проходят. Передача ссылки не требует выдавать доступ к вашему Яндекс Cloud: получатель создаёт собственную инфраструктуру.

Не передавайте `.env`, `.env.production`, `*.local`-настройки, статические ключи, ZIP деплоя, `node_modules`, браузерные профили и выгрузки рабочего пространства с реальными URL. Новый владелец создаёт свои облачные ресурсы и свои ключи; права на прежнюю инфраструктуру для этого не нужны. В репозитории ранее были реальные ссылки, поэтому удаление их из текущих файлов не удаляет их из Git-истории. Старые подписки и ключи следует перевыпустить у соответствующих поставщиков. Переписывание истории — отдельная согласованная операция.

## Условия приёмки

- `npm run release-check` проходит после установки обеих групп зависимостей.
- Сайт открывается по HTTPS; JavaScript и CSS возвращаются с корректными MIME-типами.
- Новый код доступа сохраняет проект, а второй браузер восстанавливает его.
- В опубликованном YAML есть реальные серверы **нового** владельца и нужные группы, отсутствуют `.invalid`-заглушки.
- После изменения проекта и обновления публикации URL остаётся прежним, клиент получает новый YAML.
- Закрытые бакеты не читаются анонимно; новая функция не использует старые учётные данные.
- На выбранных устройствах проверена работа в режиме правил, включая прямые сайты и проксируемые сервисы.

## Граница готовности

Это MVP для личного использования или небольшой доверенной группы. Идентификация — клиентский хеш имени и кода, без полноценной серверной аутентификации. Публикация и formatter доступны извне; лимиты, защита от злоупотреблений и ограничения адресов исходящих запросов требуют отдельного усиления перед открытым многопользовательским сервисом. Секреты хранятся на сервере, но не зашифрованы приложением; JSON/YAML-экспорт и ссылки публикации могут содержать доступ к подпискам. Подробности — в [эксплуатационной инструкции](operations.md).
